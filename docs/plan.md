## 2. 新設計との差分

### 2-1. 問題形式（concept 5章）

| | 現在 | 新設計 |
|---|---|---|
| 一往復の決断 | 2回（要旨・返答） | 1回（返答のみ） |
| 選択肢の位置 | 台詞の後 | 台詞の前 |
| 往復数 | 2固定 | 1〜5可変 |
| 正解の決まり方 | 意味の言い換えを選ぶ | 台詞の要の一語で決まる |
| 型 | なし | `keyword` / `polarity` / `multiFact` を混在 |
| 時間制限 | なし | 場面ごとの `windowMs` |
| 聞き逃し | なし | `restate` で二度目の窓 |
| 操作 | 選ぶ→決定→次へ | タップで即確定 |
| 残り数表示 | 「1 / 2」あり | なし |

`exchangesPerScene = 2` は6ファイルに埋まっている
（`scene.dart` `scene_import.dart` `skills.dart` `tree.dart` `tree_view.dart` `prompts.dart`）。

要旨（`Gist`）は27ファイルが参照している。

### 2-2. 通貨（concept 6章・11章）

全廃。`seeds` は10ファイルに出てくる
（`repository` `models` `progress_service` と、画面7つ）。

削除対象：残高、獲得、消費、表示、分野の購入、“会話”追加の課金、花と実の演出。

### 2-3. 梯子（concept 6章）

**完全に新規。** いまは難易度の概念が存在しない。

- 5軸（速度・雑音・訳・訛り・聞き直し）で合計50段超
- `current` と `max` を軸ごとに保持
- 到達判定のため直近N問の正誤を保持
- 音声側は速度変更のみ実装済み。**雑音・訛り・声の重なりは未実装**

### 2-4. 木（concept 7章）

| | 現在 | 新設計 |
|---|---|---|
| 高さ | 解いた量 | 最高到達段の合計 |
| 広さ | 分野の数 | 開いた場面の数 |
| 段階 | 6 | 20〜30 |
| 飾り | 花・実（通貨と連動） | 自然物（達成で出現、買えない） |
| 配置 | なし | 区画単位で並べ替え |

### 2-5. 場面（concept 8章）

`situation`（分野より細かい単位）が新規。解禁は梯子の進行。
いまは分野単位で、解禁は通貨。

## 3. フェーズごとの見積もり

作業量は 小 / 中 / 大 の3段階。**大** は一日仕事以上を想定。

| フェーズ | 内容 | 量 | 主なファイル |
|---|---|---|---|
| 1 | データモデル | 中 | `scene.dart` `scene_import.dart` `models.dart` `database.dart` |
| 2 | プロンプトと見本30本 | **大** | `prompts.dart` `data/scenes/*`（11ファイル） |
| 3 | 出題ロジックとUI | **大** | `scene_screen.dart`（全面）`home_screen.dart` |
| 4 | 通貨の全廃 | 中 | 上記10ファイル＋文言 |
| 5 | 梯子 | **大** | 新規 `ladder.dart`、`settings_screen.dart`、音声処理 |
| 6 | 木と環境 | **大** | `tree.dart` `tree_view.dart` |

| 8 | 検証 | 中 | テスト17ファイル |

### 一番重いところ

**フェーズ2の見本30本。** 新形式は1往復あたり
`line` `keyWord` `confusable` `replies×3` `restate` `translations` を要求し、
`multiFact` 型はさらに `facts` と `missedSlot` を持つ。
これを30本×10言語で用意する。現在の見本の構造（英語の共通部＋言語別の上乗せ）は
そのまま使えるが、中身は全部作り直しになる。

ブリーフ自身が「見本を作り込む前に生成の安定性を確認せよ」と指示しているので、
**数本の試作と人間による確認を、フェーズ2の最初の関門として置く。**
ここが崩れると問題形式そのものが成立しない。

**フェーズ5の音声。** 雑音の重畳、訛りの切り替え、声の重なりは未実装。
端末TTSで何がどこまでできるかを先に確かめる必要がある。
訛りは声の地域切り替えで可能だが、雑音の重畳は音声出力への加工が要るので、
TTS だけでは実現できない可能性がある。**ここは技術調査が先。**

## 4. 着手前に決めたいこと

ブリーフが「推測せず質問せよ」と指示している箇所、および調査で見つかった穴。

### ブリーフが明示的に確認を求めているもの

1. **お休み券を削除してよいか。** 連続日数の喪失を前提にした道具。
   連続日数そのものは記録画面に残る想定。

### 調査で見つかった、決めないと進めない穴

2. **梯子の到達判定を、軸ごとにどう帰属させるか。**
   「軸ごと独立」と書かれているが、一問を解くときは5軸すべてが同時にある設定で解く。
   速度0・雑音3で正解したとき、どの軸の直近N問に数えるのか。
   - 案A：全軸に同時に数える。上げた軸だけ判定が厳しくなる形。
   - 案B：いま一番上げている軸だけに数える。
   - 案C：軸ごとに「その設定で解いた履歴」を持ち、設定を変えると別系列になる。

   この決めがないとフェーズ5が書けない。**案Aを推奨**（実装が単純で、
   複数軸を同時に上げた人が正しく報われる）。

3. **「聞き流す」画面をどうするか。**
   旧モデルの文（`sentences`）を再生する画面で、新設計には出てこない。
   - 削除する
   - “会話”の台詞を流す形に作り直す

   推奨は**作り直し**。負荷の低い入口として価値があり、
   新形式では台詞が単体で完結しているので流用しやすい。

4. **旧モデルの残骸11テーブルを、この機会に削除するか。**
   `Items` `Sentences` `Questions` `SrsStates` `QuestionStats` `Batches`
   `Chunks` `Debates` `Attempts` `Captures` `Failures`。
   既存ユーザーのデータをリセットしてよいとブリーフに書かれているので、
   いまが一番安く消せる。削除すると `repository.dart` が大きく縮み、
   リセット処理・バックアップ・テストの各所が単純になる。
   **推奨は削除**。ただし作業量は中程度増える。

5. **既存の端末データを実際に消してよいか。**
   いま実機に入っている“会話”と記録は全て失われる。
   バックアップの書き出し機能はあるが、新形式では読めない。

6. **場面が開くペース。** 「梯子の合計段数3段ごとに1場面」が仮の値。
   序盤は梯子が速く進むので、AI へのコピペ往復が頻繁に発生する。
   儀式として置く設計だが、**序盤に連続すると負担になる**恐れがある。
   最初のいくつかは内蔵見本で埋めて、AI 往復は数場面目からにする案もある。

7. **バックアップの互換性。** 新旧でスキーマが変わるので、
   旧バックアップは読めなくなる。読み込み時に明示的に拒否するか、
   バックアップ機能自体を新形式に合わせて作り直すか。

## 5. 進め方の提案

ブリーフのフェーズ順で問題ないが、**フェーズ2の試作を先に切り出す**ことを提案する。

```
フェーズ0（完了）
  ↓
フェーズ2a：生成の試作と確認   ← 形式が成立するかの関門。ここが最重要
  ↓
フェーズ1：データモデル
  ↓
フェーズ2b：プロンプトと見本30本
  ↓
フェーズ3：出題ロジックとUI
  ↓
フェーズ4：通貨の全廃
  ↓
フェーズ5：梯子（音声の技術調査を含む）
  ↓
フェーズ6：木と環境
  ↓
フェーズ7：記録画面
  ↓
フェーズ8：検証
```

理由。データモデルを決める前に、AI が「3つとも自然で、一語だけで正解が決まる」
返答を安定して書けるかを確かめたい。書けなければスキーマの形が変わる。
試作は現在のコードに触らず、プロンプトと出力の確認だけで済む。

また、**フェーズ5の音声の技術調査**も早めに済ませたい。
雑音が重ねられないと分かれば、梯子の軸構成そのものを見直す必要がある。
フェーズ1と並行して調べられる。

## 6. 途中の状態について

フェーズ3から4の間、アプリは一時的に壊れた状態になる。
新形式の出題は動くが通貨の表示が残る、など。
各フェーズの終わりでコミットするので、戻すことはいつでもできる。

実機へのインストールは、**フェーズ4を終えた時点**を最初の区切りにするのが良い。
そこまでで「新しい問題形式で解けて、通貨が消えている」状態になる。

## 7. 決定事項（フェーズ0の結論）

| 論点 | 決定 |
|---|---|
| 旧モデルの11テーブル | **削除する** |
| 梯子の到達判定 | 軸ごとの独立バッファ。`current >= max` の軸にだけ結果を記録。N件で閾値以上なら `max += 1` してバッファをクリア。昇段は一度に1段。`max` は減らない |
| 昇段時の `current` | **自動で新しい段に追随させる**。触らなくても梯子が進み続ける。下げるのは従来どおり自由 |
| 軸の粗さ | **粗い軸の段数を増やして揃える**。訳を4段→8段、聞き直しを2段→4段。N は全軸共通 |
| 「聞き流す」画面 | **“会話”の台詞を流す形に作り直す** |
| お休み券 | **削除する**。連続日数そのものは記録画面に残す |
| 実機の既存データ | **消す**。新形式へ移行しない |
| 旧バックアップの読み込み | **廃止する**。読み込み時に明示的に拒否 |
| 場面が開くペース | 仮値（梯子の合計3段ごとに1場面）。定数として外出しし、触りながら調整 |

### 梯子の到達判定が成立する理由（記録用）

`current` は `max` を超えられないので、`current >= max` は「その軸を最高到達段のまま
使っている」条件になる。ある軸を据え置いたまま別の軸だけ上げた場合、据え置いた軸は
最初の一度だけ昇段して `current < max` となり、そこで記録が止まる。
**1段だけ先に進んで自動で固まる**ので、一度も再生していない段まで抜けることはない。
楽をしている軸には失敗も入らないので、巻き添えで止まることもない。

ただし昇段時に `current` を追随させない場合、最初の昇段の直後に全軸が
`current < max` となり、設定を触らない限り二度と進まなくなる。
上の「自動で追随させる」はこの穴を塞ぐためのもの。

### 音声の技術調査（フェーズ5の前提）

現在の依存関係に音声再生パッケージはない（`flutter_tts` のみ）。
雑音の重畳には、雑音の音源を資産として同梱し、TTS と**同時に鳴らす**second player が要る。
`audioplayers` などの追加が必要になる見込み。通信も権限も増えないが、
依存とアプリ容量は増える。フェーズ5の着手時に実機で確認する。

訛りは既存の音声選択で実現できる。速度も実装済み。
声の重なりは同じ second player の仕組みで扱える。
