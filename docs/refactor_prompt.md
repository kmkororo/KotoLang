# KotoLang 改修プロンプト（v1実装 → v3設計）

> このファイルの中身をそのまま Claude Code に貼ってください。
> 事前に `concept_v3.md` をリポジトリ内（例：`docs/concept.md`）に置いておくこと。

---

このリポジトリは KotoLang（Android・オフライン専用の英語聞き取りアプリ）です。
設計を大きく作り替えます。新しい設計は `docs/concept.md` に全文があります。**まずこれを読んでください。**

## この改修のゴール

現在の実装（`docs/concept.md` の5章「いまの仕組み」に相当）を、
6〜9章で定義された新しい設計に移行します。

## 判断基準（迷ったらこれで決める）

実装中に仕様が曖昧な箇所に出会ったら、この5つで判断してください。
これに反する実装は、たとえ動いても間違いです。

1. **機械が代われる能力を鍛えていないか。** 読解・翻訳の練習になっていたら方向が違う。
2. **一つの仕組みに、仕事を二つ持たせていないか。** 報酬でありながら記録でもある数字を作らない。
3. **決断の場所を増やしていないか。** 決断の場所は、ユーザーがやめる場所になる。
4. **待つだけで増える数字を作っていないか。** 時間経過で増えるものは一切作らない。
5. **端末の外に何か出ていないか。** 通信は一切しない。

## 絶対にやらないこと

- ネットワーク通信を追加しない（HTTP クライアント、アナリティクス、クラッシュレポート全て）
- 新しい権限を要求しない
- 放置収入・変動報酬・ガチャ的要素を追加しない
- 「自分宛てでない会話を聞く（傍聴形式）」は**今回作らない**。データ構造に拡張点だけ残す

## 進め方

**フェーズごとに進めてください。** 各フェーズの終わりでコミットし、次に進む前に要約を報告すること。

**フェーズ0を終えた時点で一度止まって、計画を見せてください。** 承認を得てから実装に入ります。

仕様が判断基準からも決められない箇所に出会ったら、**推測せずに質問してください。**

- 既存のコード構成、データモデル、画面遷移を把握する

### フェーズ1：データモデルの作り替え

“会話”（scene）のスキーマを新形式に変更します。

**現在**：各往復が「台詞 → 要旨3択 → 返答3択」
**新形式**：各往復が「返答3択（先に表示）→ 台詞（一度だけ再生）→ 返答を選ぶ」

新しいスキーマ案（調整可、ただし意図は守ること）：

```json
{
  "id": "scene_001",
  "field": "work",
  "situation": "meeting",
  "title": "会議の時間変更",
  "windowMs": 2500,
  "turns": [
    {
      "line": "Can we push it to four?",
      "keyWord": "four",
      "confusable": "three",
      "replies": [
        { "text": "Sure, four works for me.", "correct": true },
        { "text": "Sure, three works for me.", "correct": false },
        { "text": "Sorry, I can't make it at all.", "correct": false }
      ],
      "restate": "Sorry, can we move it to four instead?",
      "translations": { "ja": "..." }
    }
  ]
}
```

**`turns` の数は固定ではありません。** 1〜5往復まで可変にしてください。
現在の「2往復固定」の前提がコードのどこかに埋まっていたら、全て取り除くこと。
長い会話ほど「後半まで集中が持つか」という別の負荷になります。

**`windowMs`** … その場面で返答の窓が開いている長さ。場面ごとに変えます
（急いでいる立ち話は短く、のんびりした雑談は長い）。根幹の「間合い」に直結する値なので、
全場面で一定にしないこと。

**選択肢は3択で統一**します。2択・4択は作りません。

重要な点：

- `keyWord` / `confusable` … 正解を決める「要の一語」と「紛らわしい対」。
  **返答3択はどれも会話として自然**で、この一語を聞き分けたかどうかだけで正解が決まる。
  読むだけで消去法が使えてはいけない。

#### 往復の「型」（`type`）

**往復には3つの型があり、混ぜて出題します。** UIは3つとも共通です
（選択肢を先に読む → 音を一度聞く → 返答を選ぶ）。変わるのは
「何を捕まえないと正解できないか」だけ。

**型は難易度の軸ではありません。** 梯子で解禁したり、進行で出現率を変えたりしないこと。
最初から混ざります（仮の比率：`keyword` 50% / `polarity` 25% / `multiFact` 25%）。
難しさは速度と雑音が担当し、型は多様性だけを担当します。

**1. `keyword`（一語で割れる）** — 上のスキーマ例のとおり。音素の聞き分け。

**2. `polarity`（反転語）** — not / can't / unless / without など、聞き逃すと意味が真逆になる語。

```json
{
  "type": "polarity",
  "line": "I can't make it unless the meeting ends early.",
  "keyWord": "unless",
  "confusable": "if",
  "replies": [
    { "text": "Got it — only if it wraps up early, then.", "correct": true },
    { "text": "Great, I'll see you there.", "correct": false },
    { "text": "No problem, I'll go ahead without you.", "correct": false }
  ]
}
```

誤答の一つは、**反転語を聞き逃した人が自然に選んでしまうもの**にすること
（上の例では2番目）。これがあることで誤答が診断になる。

**3. `multiFact`（複数情報）** — 時間・場所・人などを同時に捕まえて照合する。

```json
{
  "type": "multiFact",
  "line": "Let's meet at the north gate at three, not the main entrance.",
  "facts": [
    { "slot": "place", "value": "north gate", "confusable": "main entrance" },
    { "slot": "time",  "value": "three",      "confusable": "four" }
  ],
  "replies": [
    { "text": "North gate at three. Got it.",     "correct": true },
    { "text": "Main entrance at three. Got it.",  "correct": false, "missedSlot": "place" },
    { "text": "North gate at four. Got it.",      "correct": false, "missedSlot": "time" }
  ]
}
```

**各誤答が「どの情報を取り落としたか」に一対一で対応するように作ること。**
`missedSlot` を記録し、復習で同じ弱点を優先的に突けるようにする。

**作らない型**：「含みを読む」（声の抑揚で判断するもの）は、端末TTSの抑揚が
平板なため成立しません。実装しないこと。
- `restate` … 窓を逃したときの言い直し。同じ文ではなく**少し違う言い方**にする
  （同じ文だと「二度聞ける」になり、梯子の「一度しか聞けない」段と衝突するため）。
- `situation` … 場面。解禁の単位。分野より細かい（「仕事」の中の「会議」「電話」「雑談」など）。
- 要旨の設問（comprehension）に関するフィールドは**全て削除**する。

あわせて、以下の状態を持つデータ構造を追加：

```
ladder: {
  speed:       { current: 0, max: 0 },   // 0..19 → 1.00〜1.95倍
  noise:       { current: 0, max: 0 },   // 0..10
  translation: { current: 0, max: 0 },   // 0..3 (直後/3秒後/タップ時/なし)
  accent:      { current: 0, max: 0 },
  replay:      { current: 0, max: 0 }    // 0..1 (言い直しあり / 一度きり)
}
recentResults: []   // 到達判定用。直近N問の正誤を軸ごとに保持
unlockedSituations: []
```

`current` は今の設定、`max` は最高到達段。**下げても `max` は減らない。**

### フェーズ2：AI生成プロンプトと内蔵見本

- AI に渡すプロンプトを新スキーマに合わせて書き直す。
  「3つとも自然で、台詞の要となる一語だけで正解が決まる返答を書く」ことを明示的に要求する。
- **3つの型（`keyword` / `polarity` / `multiFact`）を混ぜて生成させる。**
  型ごとに要求が違うので、プロンプト内で型ごとの指示を分けて書くこと。
  - `polarity` … 誤答の一つは「反転語を聞き逃した人が自然に選ぶもの」にする
  - `multiFact` … 各誤答が落とした情報と一対一で対応し、`missedSlot` を持つ
- **生成の安定性をフェーズの最初に確かめる。** 各型で数本だけ試作し、
  「読むだけでは絞れないか」「3つとも自然か」を人間が確認できる形で出力する。
  ここが崩れると問題形式そのものが成立しないため、
  **見本30本を作り込む前に必ず確認すること。**
- 貼り付けた JSON のバリデーションを新スキーマに更新する。
- **内蔵の見本30本を新形式で作り直す。** 既存の見本は移行せず、作り直し。
- 既存ユーザーのデータは**リセットしてよい**（マイグレーション不要）。

### フェーズ3：出題ロジックとUI

- 要旨の設問を削除し、決断を往復ごとに1回にする。
- **選択肢を台詞の前に表示する。** 読み終えたら台詞が一度だけ流れる。
- 台詞の後に窓が開く。**窓の長さは場面の `windowMs` から取る**（全場面で一定にしない）。
- 窓を逃したら `restate` が流れ、二度目の窓が開く。
  ただし梯子の `replay` が「一度きり」に到達している場合は**言い直しを発生させず即不正解**にする。
- **往復数が可変であることを前提に組む。** 1往復で終わる会話も、5往復続く会話もある。
  ユーザーには残り往復数を見せない。
- 不正解に罰はない。**コンボが切れるだけ。** 会話は止めずに進む。
- 「決定」と「次へ」の二段を廃止し、**タップで即確定＋短い取り消し窓**にする。
- 「1 / 2」のような残り数の表示を消す。
- 訳は答えた後にだけ出す（梯子の `translation` 段に従う）。

### フェーズ4：通貨の全廃と、場面解禁の接続

**通貨に関わるものを全て削除します。**

- 通貨の残高、獲得処理、消費処理、UI表示
- 通貨による分野の解禁
- 通貨による“会話”の追加生成
- 木の「花」「実」の演出（v1のもの）

代わりに：

- **場面は梯子の進行で開く。** 開いた瞬間に AI 生成の画面へ誘導する（＝解禁の儀式）。
- 「お休み券」は、連続日数の喪失を前提にした道具なので削除候補です。
  ただし明示的に決めていないので、**実装前に確認してください。**

### フェーズ5：梯子（到達判定）

- 各軸を独立して刻む。設定画面で軸ごとに上げ下げできる。
- 到達判定：**直近 N 問をその設定で一定以上正解したら次の段が開く。**
- 未決定の値は**設定ファイルの定数として外に出し、後から調整できる形**にすること。
  仮の値：`N = 10`、`正解率 = 80%`、`場面解禁 = 梯子の合計段数3段ごとに1場面`
- 最高到達段は下げても減らない。
- 「窓の中で・聞き直さず・文字も見ずに」答えたときだけ上乗せの記録を付ける。

### フェーズ6：木と環境

- **高さ ＝ 最高到達段の合計（実力）／ 広さ ＝ 開いた場面の数**
  楽な設定で大量に解いても育たないこと。解いた量では育たない。
- 木の段階を6段から**20〜30段**に増やす（見た目の刻みを細かく）。
- 達成すると木の周りに**自然物**（鳥・光・季節など）が現れる。買う飾りは作らない。
- 自然物は**区画（スロット）単位で並べ替えられる**。座標の自由配置は実装しない。
  区画の数は開いた場面の数に連動させる。
- 木は聞いている間は背景。全画面で眺められるが、**そこに用事は置かない**
  （収穫・買い物・設定を置かない）。

### フェーズ7：記録画面と「過去の自分に挑む」

記録画面は演出なしで、事実だけを静かに置く。

- 現在の設定と最高到達段、各軸ごとの到達状況
- 正答率（全期間・直近7日）、連続日数、解いた“会話”数、音だけの連続、最長コンボ
- 直近28日のヒートマップ、“会話”の一覧
- **経過時間の控えめな表示**

「過去の自分に挑む」：過去に解いた“会話”を、**今の設定で**もう一度出せるようにする。
発生のさせ方（自動で差し込む／自分で呼び出す／節目で提案）は未決定なので、
**まずは記録画面から手動で呼び出せる形**で実装し、後から差し込み方を足せるようにしておくこと。

### フェーズ8：検証

- 既存のテストを通す。壊れたものは新設計に合わせて書き直す。
- データをリセットした状態から、初回フロー →“会話”を解く → 梯子が1段上がる →
  場面が開く → AI生成の画面に入る、まで通しで動くことを確認する。
- 新スキーマの見本30本が全て読み込めることを確認する。
- ネットワーク通信が一切発生していないことを確認する。

## 今回やらないが、拡張点を残すもの

以下は後の版で足します。**今回は実装しませんが、データ構造で締め出さないでください。**

- **一本の“会話”の中で音が変わる**（途中から騒がしくなる、電波が悪くなる）。
  音響パラメータを“会話”単位ではなく**往復単位でも上書きできる**構造にしておくと、後から足せます。
- **新しい場面タイプ** … 傍聴形式（二人の会話を横で聞く）、行動を選ぶ形式
  （電話の自動音声で何番を押すか等）。`situation` に**タイプの区別を持たせられる**ようにしておくこと。
